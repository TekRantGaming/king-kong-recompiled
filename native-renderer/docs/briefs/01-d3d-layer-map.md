# Brief 01: the Direct3D layer map

## Goal

A complete, verified description of every Direct3D library function and render state the game uses, good
enough to implement each one: name, arguments (register by register, with units and enums), the device-struct
fields it reads or writes, and what the engine expects back. Output: `docs/d3d-api-map.md` grown into a full
reference, plus `docs/d3d-structs.md` (device, texture, surface, vertex / index buffer, shader, declaration
object layouts) and `analysis/d3d_api.json` (machine-readable: function -> name, args, states).

## Inputs

- `docs/d3d-api-map.md` (what is known), `analysis/d3d_entry_points.json` (the 360 entry points incl. the
  device's setter / getter tables), `analysis/device_tables.json` (table index -> function -> shadow offsets),
  `analysis/device_dump.bin` (a device struct at the title screen), the traces `analysis/d3dtrace*.log` and
  `analysis/d3dtrace_report.py`.
- The recompiled code in `kk/generated/default` (every function has its PowerPC as comments).
- The SDK's Xenos register table `C:\rexsrc\include\rex\graphics\register_table.inc` (read-only) and its
  register bitfield definitions (`registers.h`): the setters write packed GPU register values into the device's
  shadow; the register name tells you the state's meaning.
- `kk/src/dev_d3d_trace.cpp` (generated by `analysis/gen_d3d_trace.py`): per-frame call counts and argument
  logs for every hooked function. Extend it (for example to log a function's device-struct deltas) rather than
  writing a new tool.

## Method

1. For each entry in the device's setter table A (+96..+560), read the function (10-45 instructions): which
   device offset it writes, which bits, what it marks dirty. Map the offset to a register through the shadow
   layout (start from +11636 = RB_DEPTHCONTROL family, +11640 = RB_BLENDCONTROL0, +11644 = RB_COLORCONTROL,
   +11656 = PA_SU_SC_MODE_CNTL; verify against the trace values, e.g. blend factors 0x07060706).
2. Name the state from the register and bitfield (the 360 D3DRENDERSTATETYPE names: ZENABLE, ZWRITEENABLE,
   ZFUNC, CULLMODE, FILLMODE, ALPHABLENDENABLE, SRCBLEND, DESTBLEND, BLENDOP, ALPHATESTENABLE, ALPHAFUNC,
   ALPHAREF, STENCIL*, COLORWRITEENABLE0-3, HIGHPRECISIONBLENDENABLE, HALFPIXELOFFSET, VIEWPORTENABLE,
   MULTISAMPLE*, POINTSIZE, SCISSORTESTENABLE...). Table B entries are the matching getters.
3. Sampler states: table entries 97-116 are the `D3DSAMPLERSTATETYPE` setters (ADDRESSU/V/W, BORDERCOLOR,
   MAG/MIN/MIPFILTER, MIPMAPLODBIAS are confirmed); they patch bits of the sampler's fetch-constant image at
   +1152+sampler*24, which SetTexture fills from the texture object's fetch constant (+16..+36). Confirm the
   remaining twelve and write the fetch-constant bitfield table the backend will decode.
4. Resource objects: from CreateTexture (`sub_82118A68`), CreateRenderTarget (`sub_82118B88`), the vertex /
   index buffer creators and SetStreamSource / SetIndices, write the object layouts: which word holds the
   guest address, size, format, pitch, tiling, mip count, endianness.
5. Verify with a trace of each scene type: title screen, save menu, a pre-rendered video, Jack gameplay (V-Rex),
   Kong gameplay (chapter 10), the pause menu, a loading screen. Add any function that appears and is unnamed.
6. Keep `analysis/d3d_api.json` the single source for names; the other streams read it.

## Done when

Every function that appears in any of those traces has a name and an argument list, every setter maps to a
register bitfield or a documented D3D-level cache, and the object layouts are confirmed by two independent
observations (code and a dump or trace).
